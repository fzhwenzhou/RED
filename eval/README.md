# `eval/` — all-project RED evaluation

This directory evaluates every current project under `target_project/` against
its pinned RED output:

| Project | Pinned spec | Evaluation model |
|---|---|---|
| micro-ecc | [`spec/micro-ecc.json`](spec/micro-ecc.json) | synthesizable iterative multiplier RTL |
| matrixmul | [`spec/matrixmul.json`](spec/matrixmul.json) | behavioral binary32 PCPI model |
| libcrc | [`spec/libcrc.json`](spec/libcrc.json) | synthesizable iterative CRC RTL |

See [`RESULTS.md`](RESULTS.md) and [`RESULTS.json`](RESULTS.json) for measured
correctness, cycles, speedup, and available synthesis results.

This directory is also the only place RED's **performance gate** can be scored:
Gate 3 predicts a speedup, `eval/` measures one. It was over-predicting every
shipped extension by 6.3x to 7.0x, and that was visible from nowhere else.

## Scoring the performance gate

```bash
./.venv/bin/python eval/scripts/reprice.py
```

Re-prices each pinned `ISASpec` with `red.cost`, on that run's own frozen
`HotLoopReport` and `CoreProfile`, and prints the prediction beside the
cycle-accurate measurement. **Run it after any change to `red/cost.py`.** The
RTL column is the only number in this repository that came from a simulation
rather than from a model, and a cost model with nothing to check it against
drifts — this one spent three shipped extensions wrong by a factor of seven in
the same direction without anything noticing.

Findings and the changes made in response:
[RESULTS.md](RESULTS.md#does-the-performance-gate-predict-what-the-rtl-measures).

## Run everything

```bash
bash eval/scripts/run_all.sh quick  # all projects; omit full micro-ecc ECDH
bash eval/scripts/run_all.sh        # complete simulation suite
bash eval/scripts/area_all.sh       # synthesizable accelerators
```

The project-specific commands are:

```bash
bash eval/scripts/run_eval.sh                    # micro-ecc
bash eval/scripts/run_project_eval.sh matrixmul
bash eval/scripts/run_project_eval.sh libcrc
```

Complete logs and generated binaries go to ignored `eval/build/`. Each runner
returns nonzero for compilation errors, malformed vectors, C-model/RTL
mismatches, simulation traps or timeouts, firmware self-check failures, nonzero
exit status, or different baseline and extended signatures.

## Verification performed

For each instruction, `gen_vectors.py` compiles the pinned C model and emits six
corner patterns plus 200 deterministic random inputs. The shared testbench reads
each instruction's opcode, funct3, funct7, and word count from the vector file.
It runs every vector with distinct and aliased input/output blocks.

Each project then builds baseline and extended rv32im firmware, runs both on the
same PicoRV32/256 KiB SRAM model, checks the application output, and compares a
deterministic result signature before accepting the cycle counts.

## Layout

```

projects/matrixmul/          float instruction model and matrix workload
projects/libcrc/             CRC RTL and CRC workload
rtl/                         shared PicoRV32 integration, SoC, and testbench
firmware/                    micro-ecc workload and common startup/linker files
patches/                     micro-ecc source integration
scripts/run_all.sh           complete simulation entry point
scripts/run_project_eval.sh  matrixmul/libcrc runner
scripts/run_eval.sh          detailed micro-ecc runner
scripts/area_all.sh          all synthesizable area runs
scripts/reprice.py           scores Gate 3's prediction against the measurements
history/                     superseded reports
build/                       generated outputs (git-ignored)
```

## Scope and limitations

These are bounded A3/A4/A5 stand-ins. Application integration is hand-written,
not generated by an LLVM pass. The memory model is a two-cycle, cacheless SRAM,
and synthesis counts are comparative LUT/cell estimates without timing or power.

The matrixmul model is intentionally marked behavioral. Icarus uses
SystemVerilog `shortreal`; Verilator calls the checked-in DPI binary32 helpers.
It validates the spec semantics, PCPI protocol, firmware transformation, and
cycle accounting for the stated four-operation latency. It cannot provide a
credible area figure until the floating-point datapath is implemented in
synthesizable RTL.

The workloads retain the generated RED workload's dimensions and inputs but run
one outer iteration for matrixmul and libcrc. Repeating an identical kernel
20,000 or 2,000 times changes simulation duration, not the per-kernel ratio.
Micro-ecc runs one complete deterministic ECDH exchange.
