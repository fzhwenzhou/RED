
matrixmul: the profiling harness (_red_workload.c) runs N=10, ITERS=30000 multiplies, but the profile attributes all of them to ONE call of `multiply` (282.7M host instr, about 9.4 host instr per MAC). So invocations per profiled call = 30000 x (MACs per call / MACs per invocation). test.c's 2x2 is NOT the workload, and write_spec rejects invocations derived from it. The float model must be bit-exact with the non-fused app: write each mul/add as its own C statement (no contraction), canonicalize NaN to 0x7FC00000 with a mask, and keep a fixed trip count.

matrixmul round 2: the per-element FDOT10.S (words=21, 10 MAC, 3,000,000 invocations, 21 marshal words) got only 1.13x. Gate 3 charges about 26 cycles per marshalled word and 30+6*words per invocation, so a 0.24 MAC/word shape cannot pay. Replaced it with FGEMM10.S: the whole 10x10x10 GEMM in one instruction (words=200, in=A||B row-major, which matches Matrix.elements; out[0..99]=C, out[100..199]=0; mac_ops=1000; invocations=30000, one per multiply() iteration; marshal_words=300 = 200 in + 100 copied back to C). That is 2.5 MAC per word. Estimate: about 2230 + about 7700 marshal ≈ 10k cycles vs about 80k software per multiply, roughly 8x. The caller falls back to software unless the matrices are 10x10 and C does not alias A or B.
